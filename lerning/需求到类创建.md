# 从需求到类的完整流程

## 一、核心原则

### 类的设计目的

- 类是为实现某一个职责而创建的
- 类是为了方便代码的更新、扩展和维护
- 一个类只因为一种外部变化而需要修改（唯一变化量）
- 一个类只干一件事（单一职责）

### 类的职责边界

- 类的职责 = 管理描述"它是什么"的全部信息
- 类的边界 = 不管"它和别人的关系"
- 关系是协调者的事，不是某个实体类的事

### 判断标准

问自己：这条信息是描述"它是什么"，还是描述"它和别人的关系"？

```
"这本书叫 C++ Primer"     → 描述它是什么     → Book 管
"这本书被张三借了"         → 描述它和张三的关系 → Book 不管
```

## 二、从需求到类的六步流程

```
需求
 ↓  提取名词
候选对象
 ↓  问"谁会独立变化？"
识别变化源
 ↓  一个变化源 = 一个类
创建类
 ↓  每个类问"要管什么？"
确定职责边界
 ↓  职责下要做什么？
列出功能
 ↓  功能翻译成代码
写方法
```

## 三、完整示例：图书馆系统

### 需求

"做一个图书馆系统，能查书、借书、还书"

### 第一步：找名词，识别候选对象

```
图书馆、书、会员、借书记录
```

### 第二步：问"谁会独立变化？"

```
书的信息（书名、作者、ISBN）变了 → 只影响书本身，不影响会员
会员的信息（姓名、等级）变了   → 只影响会员本身，不影响书
借书规则（借期、罚款）变了     → 和书、会员都无关，是独立的规则
```

**能独立变化的，就拆成一个类。**

### 第三步：确定变化源 → 创建类

```
变化源：
  ① 书的信息变了      → Book 类
  ② 会员的信息变了    → Member 类
  ③ 借书规则变了      → LoanManager 类
```

### 第四步：确定职责边界

```
Book（管书是什么）：
  管：书名、作者、ISBN、是否可借
  不管：谁借了这本书、借期多久、罚多少钱

Member（管会员是什么）：
  管：姓名、等级、借书上限
  不管：借了哪些书

LoanManager（管两者之间的关系）：
  管：借书记录、借期规则、逾期罚款
  不管：书叫什么名字、会员叫什么名字
```

### 第五步：列出功能

```
Book（管书的信息）：
  查书名
  查作者
  查是否可借

Member（管会员的信息）：
  查姓名
  查等级
  查还能借几本

LoanManager（管借还规则）：
  借书
  还书
  算逾期罚款
```

### 第六步：功能翻译成方法

```cpp
class Book {
    string title_;
    string author_;
    bool available_;

public:
    Book(string title, string author)
        : title_(move(title)), author_(move(author)), available_(true) {}

    const string& title()  const { return title_; }
    const string& author() const { return author_; }
    bool isAvailable()     const { return available_; }
    void setAvailable(bool v)    { available_ = v; }
};

class Member {
    string name_;
    int level_;          // 1=普通, 2=VIP
    int loanLimit_;      // 借书上限

public:
    Member(string name, int level)
        : name_(move(name)), level_(level),
          loanLimit_(level == 2 ? 10 : 5) {}

    const string& name() const { return name_; }
    int level()          const { return level_; }
    int loanLimit()      const { return loanLimit_; }
};

class LoanManager {
    unordered_map<string, string> loans_;  // 书ID → 借阅者学号

public:
    bool checkout(const string& bookId, const string& memberId) {
        if (loans_.count(bookId)) {
            cout << "书已被借走" << endl;
            return false;
        }
        loans_[bookId] = memberId;
        return true;
    }

    void returnBook(const string& bookId) {
        loans_.erase(bookId);
    }

    bool isOverdue(const string& bookId) {
        return loans_.count(bookId);
    }
};
```

## 四、验证设计是否合格

### 检查单一职责

问自己：如果需求变了……

| 变化场景 | 改哪个类 | 另一个要动吗 |
|---------|---------|-------------|
| 书要加出版社字段 | Book | 不用 |
| 会员等级规则变了 | Member | 不用 |
| 借期从 30 天改成 60 天 | LoanManager | 不用 |

每个变化只涉及一个类 → 合格。

### 检验方法

写完后问自己两个问题：

1. **"如果需求 X 变了，我要改几个类？"** —— 答案应该是 1 个。
2. **"这个类里有没有和它名字无关的代码？"** —— 比如 `Book` 里出现 `checkout()`，说明职责混了。

## 五、类的演进

类的设计不是一次性的，是跟着需求演化的：

```
第一阶段：包装很简单，就是选个材料 → 一个类搞定
          ↓
第二阶段：包装扩展了，材料处理 + 检验 + 标签三个独立变化
          ↓
原来的类现在有三个变化源了 → 违反单一职责 → 要拆
```

**初始版本足够简单，等变化来了再重构。一个类能应付当前的变化量就够了，别提前过度设计。**

## 六、新理解：成员变量的本质

类的成员变量其实就是类管理的信息。

```
成员变量 = 这个类管了哪些信息
```

成员变量不是随便写的，是**职责边界画完之后自然涌现的**：

```
Book 的职责 = 管书是什么
    → 需要记录：书名、作者、ISBN、是否可借
    → 成员变量：title_, author_, isbn_, available_

LoanManager 的职责 = 管借还关系
    → 需要记录：谁借了哪本书
    → 成员变量：loans_（学号→书ID的映射）
```

**先画边界，再定成员变量——顺序不能反。** 先想"我存什么"再拼类，就是本末倒置。

## 七、难点：如何找到抽象类

### 具体类 vs 抽象类

```
具体类：看得见摸得着的东西
  宠物、商品、会员 → 说"宠物"，脑中有个画面

抽象类：看不见，但是真实存在的"动作/规则/流程"
  挂号管理、收银、借书规则 → 说"挂号管理"，脑中没有画面，但它确实在干活
```

### 怎么找到抽象类

找完名词之后，再问一个问题：**"这些实体之间怎么协作？谁在协调它们？"**

```
需求：超市收银
  ↓
实体：商品、会员、小票（看得见的）
  ↓
问：谁把商品、会员、小票串起来完成结账？
  ↓
答案：收银台/收银员在干这个活
  ↓
收银类（抽象类）
```

### 一个规律

```
具体类 = 名词（实体）
抽象类 = 动词（动作/流程）转成的名词

  扫码、算钱、扣款、出票  →  收银类
  借书、还书、罚款        →  借书管理类
  挂号、排队、分配        →  挂号管理类
```

**每个具体类都不会自己协作，一定有一个"看不见的人"在协调它们。这个看不见的人就是抽象类。**

## 八、抽象类的多种来源

### 不全是协调者，还有其他类型

| 类型 | 发现方式 |
|------|---------|
| 协调者 | 谁把实体串起来？ |
| 规则类 | 规则会独立变化吗？ |
| 接口类 | 多个类行为一样实现不同？ |
| 状态类 | 同一实体不同状态行为不同？ |

## 九、抽象类示例：电商系统

### 1. 协调者

```
需求：用户下单买商品

具体类：User（用户）、Product（商品）
  ↓
问：谁把用户和商品串起来？
  ↓
OrderManager（订单管理）
  → 管：下单、取消、查订单
  → 成员：订单列表
```

### 2. 规则类

```
需求：促销活动经常变，满 100 减 20、打八折、第二件半价...

具体类：Product、User
  ↓
问：打折规则本身会独立变化吗？
  → 会。满减改了不用动商品类，也不用动用户类
  ↓
DiscountStrategy（折扣策略）
  → 管：怎么算折扣
  → 成员：规则参数（满多少、减多少）
  → 方法：calc(double price) → 返回折后价
```

```cpp
class DiscountStrategy {
    string type_;       // "fullReduce" / "percentOff" / "halfPrice"
    double threshold_;  // 满多少
    double discount_;   // 减多少 / 折扣比例

public:
    DiscountStrategy(string type, double threshold, double discount)
        : type_(move(type)), threshold_(threshold), discount_(discount) {}

    double calc(double price) const {
        if (type_ == "fullReduce")
            return price >= threshold_ ? price - discount_ : price;
        if (type_ == "percentOff")
            return price * discount_ / 10.0;
        if (type_ == "halfPrice")
            return price * 0.5;
        return price;
    }
};
```

**没有实体对应它——"打折规则"不是人、不是物，但它是真实存在的逻辑，且会独立变化。**

### 3. 接口类

```
需求：系统支持多种支付方式：微信、支付宝、银行卡

每个支付方式都有相同行为：
  - 发起支付
  - 查询状态
  - 退款

具体实现不同，但行为一样
  ↓
PaymentMethod（支付接口）
```

```cpp
class PaymentMethod {
public:
    virtual ~PaymentMethod() = default;
    virtual bool pay(double amount) = 0;
    virtual string status() = 0;
    virtual bool refund(double amount) = 0;
};

class WeChatPay : public PaymentMethod {
public:
    bool pay(double amount) override {
        cout << "微信支付 " << amount << endl;
        return true;
    }
    string status() override { return "paid"; }
    bool refund(double amount) override { return true; }
};

class AliPay : public PaymentMethod {
public:
    bool pay(double amount) override {
        cout << "支付宝支付 " << amount << endl;
        return true;
    }
    string status() override { return "paid"; }
    bool refund(double amount) override { return true; }
};
```

**多个类有相同行为但实现不同 → 提取公共接口。**

### 4. 状态类

```
需求：订单有多个状态，每个状态行为不同

待支付 → 可以支付、可以取消
已支付 → 可以发货、可以退款
已发货 → 可以确认收货、不能退款了

一个 if-else 堆一起会很乱
  ↓
OrderState（订单状态）
```

```cpp
class OrderState {
public:
    virtual ~OrderState() = default;
    virtual void pay()    { cout << "不允许" << endl; }
    virtual void ship()   { cout << "不允许" << endl; }
    virtual void cancel() { cout << "不允许" << endl; }
};

class PendingPayment : public OrderState {
public:
    void pay() override { cout << "支付成功" << endl; }
    void cancel() override { cout << "已取消" << endl; }
};

class Paid : public OrderState {
public:
    void ship() override { cout << "已发货" << endl; }
    void cancel() override { cout << "退款中" << endl; }
};
```

**同一个实体在不同状态下行为不同 → 每个状态一个类。**

## 十、补充：观察者和工厂类

### 观察者/通知类

```
需求：商品库存变了，要通知采购部、销售部、财务部

谁在监听？多个部门，且未来可能加新部门
  ↓
Observer（观察者接口）
  → 谁关心这个事件，谁就注册进来
```

```cpp
class StockObserver {
public:
    virtual void onStockChanged(string product, int newQty) = 0;
};

class PurchaseDept : public StockObserver {
    void onStockChanged(string product, int newQty) override {
        if (newQty < 10) cout << "采购部：补货 " << product << endl;
    }
};

class SalesDept : public StockObserver {
    void onStockChanged(string product, int newQty) override {
        cout << "销售部：" << product << " 库存更新\n";
    }
};
```

**发现方式：问"一个事件发生后，谁需要知道？"**

### 工厂类

```
需求：根据用户选择创建不同类型的账户（普通、VIP、企业）

创建逻辑经常变，且和账户本身无关
  ↓
AccountFactory（工厂类）
```

```cpp
class AccountFactory {
public:
    static Account create(string type) {
        if (type == "normal") return Account("普通", 0);
        if (type == "vip")    return Account("VIP", 0.8);
        if (type == "company") return Account("企业", 0.9);
        throw runtime_error("未知类型");
    }
};
```

**发现方式：问"创建对象的逻辑本身会变吗？"**

### 更完整的清单

| 类型 | 发现方式 |
|------|---------|
| 协调者 | 谁把实体串起来？ |
| 规则类 | 规则会独立变化吗？ |
| 接口类 | 多个类行为一样实现不同？ |
| 状态类 | 同一实体不同状态行为不同？ |
| 观察者 | 一个事件谁需要知道？ |
| 工厂类 | 创建对象的逻辑会变吗？ |

**这些分类不是需要背的清单。核心方法始终是一个：问"这个东西会独立变化吗？"这些分类只是帮你在"想不到"的时候提供思考方向。**
